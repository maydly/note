01 — 시작은 '불편 목록'

무엇을 만들지는 기록이 알려 준다.

먼저 그동안의 대화 기록(백업 26개, 사람 요청 약 4,300건, 도구 사용 약 11만 5천 회)을 나눠 읽고 반복되는 불편을 셌다. 숫자가 큰 것부터 스킬이 됐다.

02 — 스킬이란: 폴더 하나짜리 매뉴얼

설명서 + 필요하면 도구.

필수

SKILL.md

맨 위에 이름(name)과 설명문(description), 그 아래에 "이럴 땐 이 순서로 한다"는 절차를 쓴다.

선택

scripts/ 폴더

절차 중 매번 똑같이 해야 하는 부분(검사·찾기·저장)을 작은 프로그램으로 넣어 둔다.

verify/
├── SKILL.md          ← 이름 · 설명문 · 절차
└── scripts/
    ├── js_check.py   ← 스크립트 문법 검사
    └── click-check   ← 버튼·입력 눌러 보기

03 — 설명문이 전부다

이름을 불러야 켜지는 방식은 실패했다.

예전에 만든 맞춤 명령들은 하나를 빼고 사용 0회였다. 사람이 이름을 기억해서 불러야 했기 때문이다. 스킬은 다르다. Claude가 지금 하는 일과 설명문을 비교해서 스스로 꺼내 쓴다. 그래서 설명문에는 "무엇을 하는지"보다 "언제 쓰는지"를 구체적으로 쓴다.

---
name: deploy-check
description: 사이트를 GitHub Pages 등에 올릴 때 쓰는 절차.
  … 실제 공개 주소에 바뀐 글자가 보이는지 확인까지 한다.
  '올려줘', '배포해', '라이브 반영', '푸시해'라고 할 때 쓴다.
---
내가 실제로 하는 말('됐어?', '반영됐어?', '올려줘')을 설명문에 그대로 넣는다. 그 말이 나오는 순간 스킬이 떠오르게.

04 — 도구 폴더: 매번 똑같아야 하는 부분

말로 시키면 매번 조금씩 달라진다.

안전

기본은 미리보기

파일을 바꾸는 도구는 기본이 "무엇을 할지 보여 주기"다. 확인 표시를 붙여야 실제로 바꾼다.

거부

위험 구역은 거절

운영 중인 공개 폴더처럼 건드리면 안 되는 곳에서는 아예 실행을 거절한다.

잠금

동시에 두 번 안 돌게

창 여러 개가 같은 도구를 동시에 쓰지 않게 잠금을 건다.

05 — 어디에 두나: 개인 범위 vs 프로젝트 범위

둔 곳에 따라 보이는 창이 달라진다.

범위위치보이는 곳
개인내 홈 폴더의 .claude/skills/이 컴퓨터의 모든 프로젝트 창
프로젝트저장소 안 .claude/skills/그 저장소에서 연 창만

함정이 하나 있었다. Claude는 프로젝트 설정을 찾을 때 git 저장소 경계에서 멈춘다. 프로젝트 폴더마다 따로 저장소인 구조라, 상위 폴더에 둔 최신 설정이 실제로 일하는 창(최근 30일 126개 중 119개)에서는 안 보였다. 그 창들에서는 몇 달 전 옛 버전이 돌고 있었다.

그래서 모든 프로젝트에서 쓸 공통 스킬은 개인 범위에 설치했다. 같은 이름이 둘 다 있으면 개인 범위가 이긴다. 프로젝트 전용 규칙이 필요한 스킬만 그 프로젝트 안에 둔다.

06 — 시험하면 고칠 게 나온다

설치 전에 샘플로 한 번씩.

1

초안(목업)

스킬 3개의 SKILL.md와 도구를 만들고, 사람이 읽을 설명서 모음을 먼저 보여 줬다.

2

샘플 시험

일부러 틀린 파일을 넣어 돌렸다. 문법 검사가 오류 줄 대신 프로그램 버전 줄을 보고하는 문제, 버전 저장 도구가 작업 폴더를 배포 구역으로 잘못 보고 거절하는 문제가 나왔다.

3

고치고 다시 시험

오류가 든 줄을 골라 보고하게 하고, "git이 무시하는 작업 폴더인지"를 확인해 작업 폴더는 허용하도록 고쳤다.

4

설치

사용자 승인 뒤 개인 범위 폴더에 복사했다. 설치한 위치에서 도구가 도는지, 지금 창의 스킬 목록에 바로 뜨는지 확인했다.

5

실사용

실제 업무(이 공부 노트 정비)에서 써 보며 다시 다듬는다.

📚 더 깊이 — 강의용 상세

탭을 눌러 펼쳐 보세요.

스킬 · 규칙 문서 · 명령은 무엇이 다른가

규칙 문서(CLAUDE.md)는 늘 읽히는 기본 원칙이다. 길어질수록 매번 읽는 양이 늘어난다. 명령은 사람이 이름을 불러야 실행된다. 스킬은 평소엔 이름과 설명문만 올라와 있다가, 필요한 순간에만 본문이 읽힌다.

그래서 "가끔 필요하지만 할 때는 정확해야 하는 절차"가 스킬에 가장 잘 맞는다. 배포 확인, 화면 확인, 버전 저장 같은 것들이다. 늘 지켜야 하는 원칙은 규칙 문서에, 절차는 스킬에 둔다.

verify 스킬이 실제로 하는 일

  • 1) 페이지 안 스크립트의 문법을 검사한다.
  • 2) 캡처 전용 브라우저로 폰(390)·PC(1280) 크기를 찍어 직접 본다.
  • 3) 버튼·입력이 있으면 눌러 보고, 페이지 오류가 있었는지 기록한다.
  • 4) 모두 통과한 뒤에야 "완료"라고 말하고, 완성본만 새 창으로 띄운다.

설명문에 '됐어?', '반영됐어?', '확인해봐', '띄워줘'를 넣어 두어, 사람이 그렇게 물으면 이 절차가 먼저 떠오른다.

스킬을 만들 때 자주 헛돈다

  • ① 설명문이 추상적. "유용한 도우미" → 언제 써야 할지 모른다. → 상황과 내가 하는 말을 그대로.
  • ② 프로젝트 안에만 둠. 다른 저장소 창에선 안 보인다. → 공통이면 개인 범위.
  • ③ 도구가 바로 파일을 바꿈. 실수 한 번이 덮어쓰기. → 기본은 미리보기.
  • ④ 시험 없이 설치. 첫 실전에서 터진다. → 일부러 틀린 샘플로 한 번 돌린다.
  • ⑤ 켜지는지 확인 안 함. 이름을 안 불러도 제때 켜지는지가 핵심이다. 내장 시험 기능으로 핵심 몇 개만 확인한다(공식 설명문 다듬기 도구는 반복 호출이 최대 약 300회라 사용량이 크다).

내 스킬 후보 찾기 (10분)

  • 최근 한 달 동안 AI에게 세 번 이상 같은 설명을 한 일은?
  • "끝났다"는데 다시 확인해야 했던 일은?
  • 매번 똑같은 순서로 해야 하는데 자주 빠뜨리는 단계는?
  • 그중 하나를 골라 "언제 쓰나" 한 문장을 먼저 써 본다. 그 문장이 곧 설명문이다.
